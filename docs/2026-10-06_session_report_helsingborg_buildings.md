## 2. Decisions and rules set by the user in this session

- **Helsingborg is the target city.** Gothenburg is dropped.
- **Nothing may be hard-coded for a city.** The project must work for any city that is fed the same kinds of data, so everything city-specific goes in `configs/cities/<city>.json` or is passed as an argument.
- **Clean data.** Repeated building IDs must be resolved automatically; the user cannot fix records by hand.
- **The user runs the pipelines.** The assistant only tests on synthetic data or reads data without writing it.
- **Run commands:** plain `python Src/Scripts/...` from the repo root, with no `cd` and no `conda`.
- **Flat roofs.** One height per building; no roof-shape reconstruction.
- **Buildings without a height get 0** and are counted, not given a guessed value.
- **Accuracy matters more than run time.**
- **About 94% of buildings with a height is enough.** The remaining gaps (buildings built after 2018, spiky heights) are accepted for now.
- **No pre-built meshes.** Unity builds the geometry at runtime. The Python mesh pipeline is kept only as reference and is not extended.
- **The old quick Unity exporters are deleted** (`export_polygon_spatial_layer.py`, `export_data_layer.py`).
- **PDAL code is kept as reference** (`pdal_pipelines.py`, `tile_index.py`) but is no longer used.
- **The manifest must be generated by a script,** never edited by hand.
- **A new Unity scene, `Helsingborg`,** where data is added step by step.

## 4. Buildings pipeline (Byggnad → clean footprints)

### 4.1 What changed

Code: `Src/pipelines/buildings/`, `Src/Scripts/run_buildings_pipeline.py`.

**Translations.**
- New module `translation.py`.
- Purposes (`andamal1..5`) have the form `"<objekttyp>;<ändamål>"`, so `config.py` now keys them by object type and then subtype (`PURPOSES`).
- Every observed value is translated, e.g. `Samhällsfunktion;Sjukhus` → *Hospital*.
- An empty subtype (`Verksamhet;`) means "unspecified".
- Unknown values are kept and reported (`unmatched_values`), never guessed.
- `Industri;Tillverkning` is in the data but not in the product description, so it is flagged `not_in_spec`.

**New columns.**
- `object_type_en` and `object_type_category` (Residential / Industrial / Public / Business / Agricultural / Ancillary / Other);
- `*_purpose_en` and `primary_purpose_category`;
- `collection_level_en`; collection-level lookups are case-insensitive;
- `main_building_flag` (bool) plus `main_building_flag_sv` (raw Ja/Nej);
- `footprint_area_m2`.

**Checked against the product description** *Byggnad Nedladdning, vektor* v1.6 (2023-02-01). Corrections:
- 15 m² is the size above which buildings are **mandatory**, not a minimum (12,657 Helsingborg buildings are smaller);
- thematic accuracy: weak for Övrig byggnad, Ekonomibyggnad and Komplementbyggnad;
- the type descriptions;
- the loader reads the layer `byggnad` explicitly.

**Repeated IDs are merged, not dropped (postprocess).**
- `objektidentitet` is a global UUID. Repeated IDs are pieces of one building that were surveyed differently; they differ only in position uncertainty and collection level.
- Postprocess steps:
  1. drop exact duplicates;
  2. drop older versions;
  3. merge the pieces: union of the geometry, attributes from the largest piece, uncertainty = maximum over the pieces, plus `source_part_count` and `collection_level_mixed`.
- `--duplicate-strategy keep_largest` exists as an option.
- Every merge is listed in `buildings_postprocess_parts.csv`.
- Decision note: `docs/decisions/2026-10-06_building-duplicate-ids-merge.md`.

**City-agnostic.** `--input` and `--output` are now required (no Helsingborg defaults).

**Tests:** `tests/test_buildings_pipeline.py`, 8/8 passing.

## 5. Building heights (`Src/pipelines/lidar_heights/`)

### 5.1 What the data turned out to be

**Laser data** (*Laserdata NH*, `Raw_data/1-Helsingborig/laserdata_nh_helsingborg/`):
- 15 LAZ tiles, 2.5 × 2.5 km;
- **scanned 2010-04-12.** "2019" in the readme and PDF is the delivery and document date, not the scan date;
- ~0.5–1.9 points/m²;
- classes: 1 unclassified, 2 ground, 9 water, 11 bridge; no building or vegetation class;
- no CRS in the LAZ headers; the sidecars say EPSG:3006.

**Surface model** (*Ytmodell från flygbild*, `ytmodell_050_helsingborg/`, extracted by the user; the zip also works):
- aerial photos from **April 2018**;
- a 0.5 m grid (~3.9 points/m²) of the top surface, class 0 only (no ground);
- pre-2019 versions have holes where image matching failed.

`ytmodell_100*` zips contain only metadata.

**Probe on 18,303 buildings:** where both sources have a height, the surface model agrees with the laser data with a median difference of about 0 and 92% within 2 m. It also covers buildings built 2010–2018. So the surface model became the primary roof source.

### 5.2 How the height is computed now

Rewritten without PDAL. For each footprint:

```
height_m = p95( z − ground(x, y) ) of the points inside the footprint
```

- **Roof:**
  - surface-model points inside the footprint shrunk by 0.5 m, because the surface smears at walls;
  - laser roof points (class 1) only where the surface has a hole.
- **Ground:** linear interpolation (Delaunay, via `matplotlib.tri`) of Lantmäteriet's own ground points (class 2) around the footprint.
  - Search distance: 15 m, widened to 50 m if too few points.
  - Points inside the footprint + 0.5 m are ignored, because they may be misclassified roof.
  - Evaluated under each roof point, so slopes are handled.
- **Why PDAL was dropped:** Lantmäteriet's ground classification is better than re-guessing it with SMRF. The surface model has no ground points, so PDAL's height-above-ground cannot work inside one point cloud. And tile-by-tile processing split buildings that cross tile edges.
- **Decision rules:**
  - surface height ≥ 1.5 m → use it;
  - the surface covers ≥ 50% of the footprint but shows < 1.5 m → **no height** (`surface_shows_ground`). The building was built after the surface date; the older laser height would belong to whatever stood there before;
  - otherwise a laser height ≥ 1.5 m → use it;
  - otherwise no height.
- **No height:** `height_m = 0`, `has_height = False`, plus a reason. There is no 2 m clamp; measured heights are kept as measured.
- **Tile edges:** buildings are processed in 1 km cells, with points read from every tile they touch.
- **Speed:** the old per-point Python loop took ~0.8 s per building (~10 h). It is now vectorised, ~13 ms per building, about 10 min for the city.

**Output columns** (after the rename):
- `height_m`, `has_height`;
- `height_source` (`surface`/`lidar`/`none`);
- `height_quality` (high = both sources agree within 1.5 m / medium / low / none);
- `no_height_reason(_code)`;
- `ground_z`, `ground_z_min`, `roof_z` (RH 2000);
- `height_p50_m`, `height_max_m`;
- `height_surface_m`, `height_lidar_m`, `height_change_flag` (> 3 m apart);
- point counts.

**Files written:**
- `buildings_lidar_added.gpkg` / `.parquet` — all building columns are kept;
- `building_lidar_qc.csv`;
- `buildings_without_height.csv`;
- `lidar_heights_summary.json` — includes the capture dates read from the tiles' JSON sidecars.

**City-agnostic:**
- all CLI paths are required;
- years were removed from the column names;
- the run warns if the surface model is older than the laser data.

**Tests:** `tests/test_lidar_heights_pipeline.py`, 5/5 (synthetic, sloped ground, new, demolished and rebuilt buildings, hole, tile edge, MultiPolygon, outside tiles). Also `--test` on the CLI.


**Code:** `Src/pipelines/unity_package/`
- `config.py`: loads and checks the city config;
- `buildings.py`: building export;
- `manifest.py`: generated manifest.

**Package written to `StreamingAssets/cities/<city>/`** (git-ignored; generated from licensed data, so it is rebuilt, never committed):
- `project_manifest.json`: generated from the `layer.json` files present in the package. Its paths are relative to the manifest's folder.
- `urban_context/buildings/geometry.bin`, **GBLD v3**:
  - IDs `building:<object_id>`;
  - height, ground elevation, has-height flag;
  - polygons with holes, as float32 x/z relative to the origin;
  - exterior rings CCW, holes CW;
  - sorted by ID, so repeated exports are identical.
- `urban_context/buildings/attributes.json`: the same column-wise layout as Unity data-layer files (typed arrays + `valid` mask).
- `urban_context/buildings/layer.json`:
  - the field list (label, group, type, unit, description);
  - counts, extent, provenance (including the height-run summary) and checksums.

**The field list is `BUILDING_FIELDS` in `buildings.py`.** It has 38 fields in 5 groups:

- **Identity:** name, other name, building number within the property, main building, Lantmäteriet ID.
- **Type and use:** type and purposes 1–5 (en + sv), category, purpose category.
- **Size and height:**
  - height (hidden when not measured);
  - height measured;
  - reason for no height;
  - footprint area;
  - ground and roof elevation.
- **Height source:** source, quality, surface height, laser height, "sources disagree".
- **Footprint survey:** surveyed at (en/sv), mixed levels, position uncertainty, merged pieces, record version date, recorded by.

**Behaviour of the field list:**
- Fields with no values at all are skipped.
- **To add a field later** (e.g. an address), add it to `BUILDING_FIELDS` and rebuild; no C# change is needed.

**Checks:**
- CRS, unique IDs and valid geometry are checked.
- The data must lie within 16 km of the origin (float32 precision).
- The binary is read back and checked against the attributes.

**Tests:** `tests/test_unity_package.py`, 5/5.
